Runner guide

Corvex-RedOps — user manual

Corvex-RedOps assesses every asset type from one place: web apps, APIs, mobile & desktop apps, infrastructure, network devices, firewalls and system hardening. Sign in, point it at a target, and it discovers the surface, tests it against the OWASP Top 10, and reports prioritised findings.

1 · Sign in

First-run admin is admin; no password ships — a strong one is generated on first run and printed once to the API log. Change it after first login, or create a separate workspace with Create workspace.

2 · Scan live targets (web / API / infra)

  1. Open New scan → Scan targets.
  2. Name the engagement and record who authorised it.
  3. Enter targets, one per line. Prefix the type when helpful: web=https://app.example.com, api=https://api.example.com, wordpress=…, infra=192.0.2.0/24.
  4. Choose scope enforcement (Warn to start), then Create & open → Run scan.

3 · Test an API (upload a spec + token)

  1. New scan → Upload & scan, asset type API.
  2. Select the OpenAPI/Swagger file, set the Base URL, and paste an access token.
  3. Add a second token + object IDs to unlock cross-tenant / access-control (BOLA) testing.
  4. Tick Enable active testing for injection & brute-force checks (authorized targets only), then Upload & scan.

4 · Assess a mobile / desktop app or device config

Pick the matching asset type and upload the file — Android/iOS package, desktop binary, or a network-device / firewall / hardening configuration. Analysis starts automatically. For live mobile instrumentation, grab the Dynamic kit.

5 · Read the results

  • Severity tiles & bars — the risk breakdown at a glance.
  • OWASP coverage — which Top-10 (web & API) categories were exercised; red = a critical finding.
  • Findings table — risk score, severity, title, endpoint and OWASP mapping. Chains group related findings.
  • Open report — a client-ready report (executive summary, evidence, remediation, compliance mapping).

6 · Good practice

  • Only scan assets you are authorised to test; record the authorisation in the engagement.
  • Keep active testing off for production unless you have a maintenance window.
  • Re-run an engagement any time to track remediation over time.
